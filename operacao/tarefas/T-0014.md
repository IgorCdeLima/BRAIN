# T-0014 - Travar o estagio lock e restringir o servico lock (SEC-0007, SEC-0008)

<!-- Worktree no Orca: T-0014-lock-endurecido -->

## Objetivo

1. Corrigir o SEC-0007: a ferramenta que gera os hashes (pip, pip-tools e as indiretas) tambem instalada com versao exata e hash.
2. Corrigir o SEC-0008: o servico `lock` sem root e sem escrita no repositorio inteiro (nada de `.githooks/`, `.env` ou `app/`).

## Contexto

- Origem: revisao da Seguranca na T-0009 (commit avaliado `30504a2`; merge da T-0009 em `d362236`). Os dois SEC sao de severidade baixa e nao bloquearam a T-0009; a Seguranca sugeriu tratar os dois juntos.
- Registros: `qualidade/seguranca/SEC-0007.md` (CWE-829) e `qualidade/seguranca/SEC-0008.md` (CWE-250), com reproducao e recomendacao de correcao.
- Decisao de base: `docs/adr/ADR-0003 Dependencias travadas com hash via pip-tools.md`. README e `CLAUDE.md` do lab descrevem `docker compose run --build --rm lock` (o `CLAUDE.md` depende do ADM-0014).
- **Ordem:** depois da T-0008 (mesmo `Dockerfile` e `docker-compose.yml`). Criado pelo Coordenador com o "sim" do humano em 2026-10-01; a T-0008 ficou como estava.
- Notas do Brain: [[CWE-829 dependencia sem versao e sem hash se evita com requirements travado com hashes]], [[CWE-250 container como root se evita com USER sem privilegio e cuidado com a posse de volumes]]; candidato do Inbox (pista): `Servico de lock no Compose montando o repositorio inteiro alcanca os hooks do Git e executa no host`.

- `seguranca: sim` (dependencias e privilegio de container). Sugestao para a triagem: dispensar a analise de ameacas previa (os dois SEC ja trazem ameaca e correcao); manter a revisao da Seguranca.

## Criterios de aceite

**SEC-0007 - estagio lock travado**

- [ ] `requirements-lock.in` (`pip-tools==7.6.1`) e `requirements-lock.txt` gerado por `pip-compile --generate-hashes --allow-unsafe` dentro do container (inclui `pip` e as indiretas: build, click, packaging, pyproject_hooks, setuptools, wheel), com cabecalho dizendo o comando que o gera.
- [ ] Estagio `lock` instala com `pip install --no-cache-dir --require-hashes -r requirements-lock.txt`.
- [ ] `pip freeze --all` da imagem `lock` so tem pacotes presentes em `requirements-lock.txt`, com a mesma versao (registrar a contagem).
- [ ] Teste negativo: remover um hash do `requirements-lock.txt` numa copia -> `docker compose build lock` falha.
- [ ] Decisao registrada na Entrega sobre fixar as imagens base por digest (`@sha256:`): feito ou nao, e por que (se for decisao do humano, levar em "Passos do humano").

**SEC-0008 - servico lock restrito**

- [ ] O servico `lock` nao roda como root: `docker compose run --build --rm lock id -u` diferente de 0.
- [ ] O servico so ve os arquivos de dependencia: os `.in` montados so leitura e escrita apenas nos `requirements*.txt` (ou numa pasta de saida). Teste: `docker compose run --rm lock sh -c 'touch /work/.githooks/x'` falha; `.env` e `app/` nao estao visiveis no container.
- [ ] `pip-compile` com `--pip-args "--only-binary=:all:"` (ou justificativa registrada se nao der).
- [ ] `lock` regenera os tres travados **identicos** aos commitados (salvo atualizacao intencional registrada) e os arquivos gerados ficam com o dono do usuario no host (nao root).

**Geral**

- [ ] Comentarios do `Dockerfile`, dos `.in` e o README dizem `docker compose run --build --rm lock`.
- [ ] `docker compose run --build --rm test`, `lint` e `audit` passam; `GET /health` 200.
- [ ] Se o `CLAUDE.md` do lab precisar mudar, texto exato em "Pedidos ao Coordenador".

## Restricoes / o que NAO fazer

- Nao editar `requirements*.txt` a mao; nao gerar travados fora do container.
- Nao mudar versoes das dependencias da aplicacao (fora do escopo).
- Testes de escrita indevida so em copia descartavel ou com arquivo vazio inofensivo; nunca alterar `.githooks/` de verdade.
- Nunca `down -v`.
